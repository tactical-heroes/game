# Project Structure

## Purpose

This document defines where project files belong and how local Unity packages
are organized.

Local packages are the main ownership boundary. Folders should make that
ownership obvious.

The project is one Unity application composed from isolated feature packages.

## Repository Layout

Source areas: `Assets/`, `Packages/`, `ProjectSettings/`, `Documentation/`,
`BuildScripts/`, `.github/`.

`Library/`, `Temp/`, `Logs/`, and user-local folders are generated by Unity.

## Package Categories

The project uses Bootstrap, Foundation, and Feature packages.
Package names use lowercase reverse-DNS, for example
`com.company.game.feature.inventory`.

Feature names should represent business capabilities, not technical buckets.
See `Documentation/conventions/naming.md`.

## Bootstrap Package

There is one bootstrap package. It owns application startup, root dependency
registration, feature installer loading, initial routing, and global
application lifetime.

Feature packages must not depend on Bootstrap.

## Foundation Package

Foundation contains shared abstractions and primitives used by multiple
features.

Allowed: shared value abstractions, cross-cutting interfaces, generic utilities
with stable ownership, and reused Presentation/Application/Domain base
abstractions.

Forbidden: feature business logic, convenience dumping ground code, UI for one
feature, and infrastructure implementation chosen by one feature only.

## Feature Packages

A feature package owns one business capability and may contain:

```text
Packages/com.company.game.feature.inventory/
  package.json
  Runtime/
    Contracts/
    Domain/
    Application/
    Infrastructure/
    Presentation/
    Composition/
  Editor/
  Tests/
    Editor/
    Runtime/
```

Small features may start with fewer folders or a single runtime assembly. Split
when complexity or compiler-enforced boundaries justify it.

## Public API

The public API of a feature is its Contracts and installer.
Other features must not depend on its Domain, Application, Infrastructure,
Presentation, or Composition internals.

Allowed dependencies: `Feature -> Foundation`,
`FeatureA -> FeatureB.Contracts`, `Bootstrap -> Feature Composition`.

Forbidden dependencies: `Feature -> Bootstrap`, `Foundation -> Feature`,
`FeatureA -> FeatureB internals`.

## Assets

`Assets/` contains Unity project assets that are not owned by local packages or
must live in the Unity project root.

Recommended structure:

```text
Assets/
  Art/
  Audio/
  Scenes/
  Settings/
  AddressableAssetsData/
  Localization/
  StreamingAssets/
  ThirdParty/
```

Scenes live in `Assets/Scenes`. Addressables configuration lives in
`Assets/AddressableAssetsData`.

Do not put feature source code in `Assets` when it belongs to a local package.

## Runtime, Editor, Tests

Runtime code belongs under package `Runtime/`.
Editor-only tools live in `Editor/` and editor assemblies.

Tests live in package-local `Tests/Editor` or `Tests/Runtime`.
Pure Domain and Application tests should normally be Editor tests. Scene,
Addressables, and Play Mode behavior belong in Runtime tests.

## UI Colocation

Keep UI Toolkit files near the screen or component that owns them:

```text
Presentation/Screens/Inventory/
  InventoryScreen.cs
  InventoryView.uxml
  InventoryView.uss
  InventoryViewModel.cs
  InventoryScreenState.cs
```

## What Does Not Belong

Do not put generated build output, temporary diagnostics, package-owned tests,
or business logic directly in `Assets/`.

Do not put global Unity project settings, production scenes, generated Unity
folders, or premature shared code in feature packages.

## Review Checklist

Before adding files or packages, verify:

1. The owner feature or project area is clear.
2. Runtime and Editor code are separated.
3. Public API and dependencies follow architecture rules.
4. Tests are close to the code they cover.
5. Temporary files are not committed.
